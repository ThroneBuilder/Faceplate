# Implementation Plan: Gallery Platform Expansion

**Branch**: `007-gallery-platform` | **Date**: 2026-06-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/007-gallery-platform/spec.md`

## Summary

Expand the Faceplate gallery system across five areas: (1) five named galleries with public/restricted nav in every page header; (2) live two-layer backing plate preview during face shaping; (3) required name field on sharing (random default, public-gallery-only); (4) submission name displayed as hover tooltip; (5) full JSON data export replacing CSV; (6) four-button admin controls per cubby (Move↑, Select, Download↓, Delete) plus bulk operations header bar.

All changes are client-side or first-party server-side. No third-party data transmission. No mosaic pipeline changes.

## Technical Context

**Language/Version**: TypeScript 5.x (strict), Node.js 22+ (server), browser ES2020 (client)

**Primary Dependencies**: Astro 4.x hybrid SSR, `@astrojs/node` v8.3.4 adapter, Vitest 1.x (tests)

**Storage**: Flat-file JSON manifest (`gallery-data/{slug}/submissions.json`) + PNG + JSON files per submission

**Testing**: Vitest unit tests for new pure functions (`computePlateLayout`, `generateRandomName`, `moveSubmissions`)

**Target Platform**: Node.js SSR server + browser client

**Performance Goals**: Plate layout preview updates within 1s of face mask change; tooltip appears ≤300ms; admin tooltip ≤500ms

**Constraints**: No third-party data transmission (Constitution §I); TypeScript strict throughout; no new npm dependencies required

**Scale/Scope**: 5 galleries, O(100) submissions per gallery; plate layout computed on a 32×36 grid (~1,152 cells)

## Key Implementation Notes

### Backing Plate Algorithm
See `research.md` Decision 1 for full algorithm detail. The function signature:
```typescript
computePlateLayout(mask: FaceMask, mosaicWidth: 32, mosaicHeight: BrickHeight): PlateLayoutResult
```
Lives in `src/lib/mosaic/plate-layout.ts`. Runs in the browser — invoked from the face-shaping section of `index.astro`'s client-side script block whenever the mask changes. No Web Worker needed (32×36 grid, greedy scan is <1ms).

### Plate Preview Rendering
Two `<canvas>` or `<svg>` elements stacked vertically to the right of the face-shaping canvas. Each cell is drawn as a filled rectangle with a 1px border. If a plate piece is ≥2 studs tall AND ≥4 studs wide, render its dimensions centered inside (e.g., "2×4"). Cell size: scale to fit roughly the same height as the face-shaping canvas thumbnail.

### Admin Reorder (promote.ts update)
The current implementation stamps `timestamp: 0` for promotion. The new 3-state logic needs to know the face's current position to determine which state it's in. Add a helper `getSubmissionPosition(dataDir, slug, uuid): { batchIndex: number; isFirstInBatch: boolean; isAbsoluteFirst: boolean }` to `submissions.ts`. The API response includes `action` so the client can show confirmation without reload delay.

### JSON Data File
Built in `index.astro` client-side at share time. Includes mosaic grid, both plate layouts, and parts list. Sent as `mosaic_json` File in FormData. Server saves as `{uuid}.json` — replaces the existing `{uuid}.csv` pattern. The download endpoint (`GET /api/gallery/image/{slug}/{uuid}.json`) reuses the existing image endpoint pattern.

### Backward Compatibility
- Legacy `SubmissionRecord` entries without `name` field: `name` defaults to `''` — tooltip shows nothing rather than "undefined"
- Legacy `.csv` files: not deleted in this phase; `.json` is the new format going forward
- The `promoteSubmission()` function (sets timestamp=0) is superseded by the new 3-state reorder; keep the old function signature for the existing `/api/gallery/promote` endpoint while updating its logic
