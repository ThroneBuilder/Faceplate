## Summary

Three public gallery pages (`/hall-of-faces`, `/hall-of-nobles`, `/brickcon-2026`) served by a single dynamic SSR Astro page. Each page shows the gallery name, description, and an "Add your face" link back to faceplate.me with the gallery pre-filled. Below the header, one or more Hall.JPEG (1923×1302 px, 2-row × 3-column) composites are rendered client-side via Canvas 2D — each canvas holds up to 6 submitted mosaics placed into calibrated cubby positions. Submissions are persisted on a server-side volume outside the build output. The faceplate.me main page gains a `?hall=` parameter pre-fill for the "Add to Group" field.

---

## Technical Context

**Language/Version**: TypeScript strict, Astro 4.x hybrid output (already configured from Phase 005)

**Primary Dependencies**: None new — uses existing Canvas 2D (browser), existing SSR infrastructure, existing `gallery-groups.json` config pattern

**Storage**: Server-side persistent volume (`GALLERY_DATA_DIR` env var, default `/data/gallery` in production, `gallery-data/` locally). PNG files and JSON manifest stored at that path.

**Testing**: Vitest (node env) for pure functions in `src/lib/gallery/submissions.ts`. Canvas rendering and SSR pages require manual/browser testing.

**Target Platform**: Render.com with persistent disk mounted at `/data/gallery`; local dev uses `./gallery-data/` (gitignored)

**Performance Goals**: Gallery page loads within 3 s (SC-001). Canvas compositing completes within 3 s per page in modern browsers.

**Constraints**: Client-side Canvas compositing only (constitution Principle II). No original image data stored — only the masked mosaic PNGs that users explicitly submitted.

## Implementation Notes (for /speckit-tasks)

### Environment variable

`GALLERY_DATA_DIR` — path to persistent storage root. Set to `/data/gallery` on Render.com; set to `./gallery-data` for local dev. Must be read by `submissions.ts`, the submit route, and the image-serve route.

### `submissions.ts` module (pure, node-testable)

```typescript
export function readSubmissions(dataDir: string, slug: string): SubmissionRecord[]
export function appendSubmission(dataDir: string, record: SubmissionRecord): void
```

`readSubmissions` reads `{dataDir}/submissions.json`, parses, filters by slug, sorts by timestamp ascending. `appendSubmission` reads the file, appends the record, writes back.

### Cubby constants

```typescript
// src/lib/gallery/cubby-slots.ts
export const HALL_W = 1923
export const HALL_H = 1302
export const HALL_MOSAIC_SCALE = 0.10   // 32-brick mosaic = 10% of image height

export const CUBBY_SLOTS = [
  { row: 0, col: 0, alcoveCx: 423,  alcoveCy: 391 },
  { row: 0, col: 1, alcoveCx: 962,  alcoveCy: 391 },
  { row: 0, col: 2, alcoveCx: 1500, alcoveCy: 391 },
  { row: 1, col: 0, alcoveCx: 423,  alcoveCy: 911 },
  { row: 1, col: 1, alcoveCx: 962,  alcoveCy: 911 },
  { row: 1, col: 2, alcoveCx: 1500, alcoveCy: 911 },
]
```

### `gallery-composite.js` — client script

Loaded deferred on every gallery page. Reads `window.GALLERY_BATCHES`. For each batch:
1. Load Hall.JPEG (module-level cache)
2. `ctx.drawImage(hallImg, 0, 0, HALL_W, HALL_H)` — background
3. `brickPx = Math.round(HALL_H * HALL_MOSAIC_SCALE / mosaic.height)` = 4 for 32-brick mosaics
4. For each non-null URL (positions 0–5): load PNG, draw centred on `(alcoveCx, alcoveCy)` with shadow gradients
5. Null slots: skip

### Phase 005 route migration

Updated `submit.ts` returns `redirectUrl: "/{slug}"` (was `/gallery/{slug}`). The old `src/pages/gallery/[slug].astro` stub becomes a 301 redirect.

### Cubby calibration — pre-measured, verify during implementation

Coordinates are pre-measured. Render the debug overlay (6 red rectangles) to confirm alignment. If any slot is off, adjust `CUBBY_SLOTS`. Remove overlay before shipping.
